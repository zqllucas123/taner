## 〇、技术底座与统一约定

真实后端为 **微信云开发（CloudBase）云函数**，而非架构文档中规划的 MySQL + Node.js（那是备选/演进方向）。本设计以**当前已落地的 CloudBase 形态**为准。

| 维度 | 约定 |
| ---- | ---- |
| 后端形态 | 每个业务域一个云函数，`action` 字段路由子操作（`exports.main(event)` 内 `switch(action)`） |
| 统一响应 | `{ code, message, data }`，`code === 0` 为成功；前端 `services/cloud.ts` 的 `callFunction` 已封装解包与错误 toast |
| 身份 | `cloud.getWXContext().OPENID` 取当前用户，`users` 集合按 `openid` 反查 `_id` |
| 集合命名 | 小写下划线复数（`user_coupons`、`stall_qrcodes`、`order_items`）；**字段名 camelCase**（`stallId`、`soldCount`、`minSpend`、`deletedAt`） |
| 金额 | 元为单位的 Number；折扣券 `discount` 存**折数**（8.5 折 → `8.5`） |
| 并发扣减 | 库存/领券用「`where(条件) + update` 判断 `stats.updated > 0`」实现原子 CAS，杜绝超卖/超领 |
| 内容安全 | 用户生成内容（许愿、评论、券标题）统一过 `security.msgSecCheck` v2，异常放行不阻断主流程 |
| 前端 | Taro 3 + React 18 + Zustand（`stores/*`）+ NutUI；分包 `packageCustomer` / `packageSeller` |

## 一、店铺简介（店铺头卡）

### 1.1 效果图拆解

对应效果图顶部绿色卡片：店名「老周秘制铁板鱿鱼」+ 品类标签「小吃美食」+ 评分「★4.9」+ 一句话简介 + 营业时间 + 距离。

### 1.2 数据来源

来自 `stalls` 集合，经 `stall` 云函数 `get`（顾客扫码/点卡片进店时调用）。核心字段：

| 展示位 | 字段 | 说明 |
| ---- | ---- | ---- |
| 店名 | `name` | |
| 摊主称呼 | `ownerName` | 如「周师傅」 |
| 品类标签 | `category` | 枚举：小吃美食/服饰饰品/生鲜果蔬/手工文创/日用杂货 |
| 评分 | `rating` | 默认 5.0，由订单完成后好评聚合 |
| 简介 | `description` | 一句话卖点 |
| 营业时间 | `stallTime` | 文案「17:30 - 00:30」 |
| 出摊状态 | `status` / `statusText` | active 出摊中 / upcoming 即将出摊 / offline 已收摊 |
| 距离 | 前端计算 | 由 `latitude/longitude` 与用户定位 Haversine 计算，不入库 |
| 公告 | `announcement` | 摊位公告条 |
| 实景图 | `vibeImage` / `vibeImageOpt` | AI 优化前后对比 |

### 1.3 摊主侧管理

摊主端 `stall-setting` 页 → `stall` 云函数 `update`（仅校验 `stall.userId === 当前用户`）。出摊/歇业一键切换走 `updateStatus`（同步影响商品可预定性、地图标记灰显）。

### 1.4 顾客侧展示逻辑

- 进店优先 `stall.get`，命中后按 `status` 渲染状态徽章；`offline` 时商品区置灰、隐藏「预约」按钮并提示「摊主歇业中，可先许愿/领券」。
- 距离由 `useLocation` hook 提供当前坐标，前端算好后格式化为「150 米」。

### 1.5 待补充

- `rating` 真实聚合（当前为默认值）：订单 `complete` 后触发好评评分，落 `stalls.rating` 与评价明细。
- 店铺主页首屏聚合接口（**可选优化，非必需**）：当前 stall-detail 分 4 次 `callFunction`（stall/product/coupon/wish）已可用；如需降冷启延迟，可在 `stall` 增加 `detailBundle` action，一次返回 `stall + 有效券 + 进行中拼团 + 上架商品 + 热门许愿`。优先级降至 P2，避免过早优化。

## 二、优惠券

### 2.1 竞品参考

| 平台 | 关键设计 | 可借鉴点 |
| ---- | ---- | ---- |
| 美团/大众点评 | 商家券 + 平台券；满减券、代金券、新客专享、关注领券、支付后弹券 | 满减门槛（`minSpend`）、领取场景多样化 |
| 拼多多 | 无门槛小额券高频发放、分享助力领券 | 分享裂变领券 |
| 瑞幸/星巴克 | **支付成功自动发下一张券**（复购钩子）、会员积分兑券 | 收款自动发券、积分兑券 |

结论：地摊场景应主打「**到店/扫码领 + 收款后自动发 + 新客券**」三条低门槛路径，摊主零操作即可持续复购召回。

### 2.2 优惠券模型（已实现）

`coupons`（券模板，摊主创建）+ `user_coupons`（领取记录，一人一份）。

```
coupons:      { stallId, title, type, discount, minSpend, totalCount, claimedCount,
                scene, expiry, status }
user_coupons: { userId, couponId, stallId, status, orderId, claimedAt, usedAt }
```

- `type`：`discount` 折扣（`discount`=折数）/ `cash` 现金直减 / `gift` 赠品
- `scene`：`manual` 手动领 / `auto_pay` 收款自动发 / `share` 分享领 / `new_customer` 新客券
- `totalCount = -1` 表示不限量；`status`：active/paused/expired

### 2.3 摊主侧：分发与管理

摊主端 `coupon-manage` 页 → `coupon` 云函数 `create` / `update`（暂停·恢复）/ `list?mine=true`。

**创建券配置项：**

| 配置 | 字段 | 示例 |
| ---- | ---- | ---- |
| 券名 | `title` | 「到店惊喜满 20 减 3」 |
| 类型 | `type` | 现金 3 元 / 8.5 折 / 送鱿鱼须 |
| 门槛 | `minSpend` | 满 20 元可用 |
| 面额 | `discount` | 3 / 8.5 |
| 发放总量 | `totalCount` | 100（-1 不限量） |
| 领取场景 | `scene` | manual / auto_pay / new_customer / share |
| 有效期 | `expiry` | 到期时间 |

**分发方式（对应 `scene`）：**

1. **到店领取（manual）** — 效果图「点击一键领取」，顾客进店/扫聚合码后手动领；聚合码 `features` 含 `coupon` 时进店直达领券。
2. **收款自动发（auto_pay）** — 订单 `complete` 后系统自动为该顾客发一张 `auto_pay` 券，钩住下次复购（需在 `order.complete` 内挂发券逻辑）。
3. **新客券（new_customer）** — 顾客首次进该摊自动发（判断该 `userId` 在本 `stallId` 无历史订单）。
4. **分享领（share）** — 顾客分享店铺卡片，好友通过分享链接领取。

**管理能力：** 列表看「已发放/已领取/已核销」三态统计；一键暂停/恢复（`update` 改 `status`）；到期自动置 `expired`。

### 2.4 顾客侧：领取与核销

- 领取 → `coupon` 云函数 `claim`：`user_coupons` 有 `uk_user_coupon` 唯一约束（**一人限领一张**）；库存用 `claimedCount < totalCount` 条件 + `inc` 原子扣减，防超领。
- 我的券 → `coupon.list?owned=true`（带券快照 + status 过滤）；页面 `my-coupons`。
- 核销 → **已在 `order` 云函数 `reserve` 内实现**：下单传 `couponId`，校验归属/未使用/适用摊位/满额，算 `discountAmount`，成单后置 `user_coupons.status='used'` 并回填 `orderId`。

### 2.5 状态机

```
user_coupons: unused ──下单核销──> used
                  └──到期───────> expired
coupons:      active ⇄ paused ──到期──> expired
```

## 三、邻里拼团

### 3.1 竞品参考

| 平台 | 机制 | 借鉴点 |
| ---- | ---- | ---- |
| 拼多多 | 发起团 → 邀请好友 → 满员成团 → 各自付款发货；未成团退款 | 经典「发起-邀请-成团」骨架 |
| 美团拼好饭 | 同商圈多人拼一单降低履约成本 | 同城/同商圈聚合 |
| **闲鱼「拼团」** | 针对谷圈/饭圈：团长「发拼团」一键发起（自动排单、一键补邮、批量发货、**开团无上限**）→ 进入**拼团广场**借公域流量「摇人成团」→ 时间+人数限制 → 成团后统一支付发货 → **未成团可重开或原价买** | ①团长视角发起 ②拼团广场（公域曝光成团）③时间/人数双约束 ④失败兜底 |

**闲鱼的关键差异**：它把拼团做成「团长开团 + 公域广场找人」，而非仅私域邀请。对地摊「邻里」场景，我们取其**公域广场凑团**思路——把进行中的团展示在店铺主页 + 同城扫街页，让邻居就近拼。

### 3.2 本项目模式定义

- **成团规模**：2–3 人小团（`targetCount`），邻里近距离，主打「凑人享超低价 + 到店自提」。
- **发起方**：摊主预设拼团活动（选商品/成团价/人数/有效期/限量）→ 顾客「一键参团」，第一个参与者即团长。
- **履约**：不发货，成团后各成员生成拼团订单 + 取货码，到摊自提（复用模块五）。

### 3.3 数据模型

```
group_buys:              { stallId, productId, productName, price(成团价),
                           targetCount, currentCount, expiryHours, expireAt,
                           status: active|completed|expired|cancelled }
group_buy_participants:  { groupBuyId, userId, orderId, joinedAt }   // uk(groupBuyId,userId)
```

**并发人数用 CloudBase 原子 CAS 承载**（对齐 `order/index.js` 已验证的库存扣减写法，**本栈无 Redis，不用计数键**）：
`where({ _id, status:'active', currentCount: _.lt(targetCount) }).update({ currentCount: _.inc(1) })`，判 `stats.updated > 0` 即抢名额成功；命中 `targetCount` 的那一笔负责触发成团转单。

### 3.4 待建 `groupbuy` 云函数（action 设计）

| action | 角色 | 说明 |
| ---- | ---- | ---- |
| `create` | 摊主 | 创建拼团活动（校验商品归属本摊；写 `expireAt = now + expiryHours`） |
| `list` | 顾客/摊主 | `stallId=xxx` 看店铺进行中的团（效果图「发起的邻里拼团」）；`mine=true` 摊主看本摊所有团 |
| `join` | 顾客 | **参团/发起**：`uk(groupBuyId,userId)` 防重复参团；原子 CAS `where({_id,status:'active',currentCount:_.lt(targetCount)}).update({currentCount:_.inc(1)})` 抢名额并判断是否达 `targetCount` → 达标置 `completed` 并**在本云函数内**为每位成员建拼团订单（`orders.type='groupbuy'`，逐份 `genPickupCode` + 原子扣库存 + 写 `order_items`）；写 `group_buy_participants` |
| `detail` | 顾客 | 团详情 + 参与者头像列表 + 剩余名额/倒计时 |
| `cancel` | 摊主 | 下架未成团活动 |

**成团/超时处理：**
- `join` 命中最后一名 → 事务内批量转订单 + 发「拼团成功」订阅消息（模块五通道）。
- 到期未满员 → 云开发**定时触发器**扫 `expireAt < now && status='active'` 置 `expired`，已付定金则退款；参考闲鱼「可重开/原价买」，顾客侧提供「再开一团」与「单独预约原价」入口。

### 3.5 摊主侧配置与管理

摊主端新增拼团管理入口（可并入 `marketing` 营销中心）：
- **配置**：选在售商品 → 设成团价（低于零售价）/ 成团人数 2–3 / 有效期（如 11 小时，见效果图「还剩 11 小时」）/ 限量。
- **管理**：看进行中的团、已成团数、待成团差几人；一键开新团/停团；成团后订单自动进入制作队列（模块五）。

### 3.6 顾客侧流程

```
店铺主页看到「邻里拼团」卡 → 一键参团(join) → 成为团长/参团者
  → 分享小程序卡片邀请邻居(Taro 分享) → 实时看人数进度/倒计时
  → 满员成团 → 生成拼团订单+取货码 → 到店自提
  （超时未成团 → 退款/再开团/原价预约）
```

### 3.7 前端 `groupbuyStore`（待建）

`activeGroups[]`（按 stallId）、`fetchByStall`、`join`、`detail`；参团后刷新人数与自身参与态。

## 四、在售商品选购（店铺购物车）

### 4.1 竞品参考：美团外卖

美团外卖购物车核心特征，直接对标本模块：
- **以店铺为单位**：购物车绑定单个店铺，跨店结算需分开；切店加购时提示「重新下单会清空购物车」。
- **常驻底部结算栏**：左侧购物车图标 + 数量角标 + 合计金额，右侧「去结算」；未达起送价时置灰提示差额。
- **商品行加减器**：`+/−` 步进，实时联动底部合计与角标飞入动画。
- **规格/多规格**：多规格商品弹层选规格再加购（地摊多为单规格，可简化）。

**地摊差异**：无配送、无起送价，「去结算」= 生成**到店自提预约单**（对接模块五 `reserve`），而非外卖配送单。

### 4.2 购物车方案：本地态为主

地摊购物车生命周期短、强前端交互，**建议纯前端 Zustand `cartStore` + 本地持久化**（`Taro.setStorage`），不落云端，结算时才落 `orders`。理由：减少往返、离线可加购、降低云函数调用量。

```ts
// stores/cartStore.ts（待建）
interface CartItem { productId: string; name: string; price: number; qty: number; image?: string }
interface CartState {
  stallId: string | null                       // 当前购物车所属摊位（保证单店）
  items: Record<string, CartItem>              // productId -> item
  add(stallId, product): void                  // 跨店加购 → 弹确认后清空重置
  inc(productId): void
  dec(productId): void                         // 减到 0 自动移除
  clear(): void
  totalQty: number                             // 派生
  totalAmount: number                          // 派生
}
```

### 4.3 关键交互

1. **单店约束**：`add` 时若 `stallId` 与当前不同 → NutUI Dialog「切换店铺将清空当前购物车？」确认后 `clear` 再加（美团同款）。
2. **底部结算栏组件** `CartBar`：常驻 stall-detail 底部，展示总数角标 + 合计 + 「去结算(N)」；空车隐藏。
3. **结算校验**：进入 reserve 前用 `product.list` 拉最新库存/上架态，对失效/超库存商品标红并提示调整（防本地态与云端不一致）。
4. **持久化**：`cartStore` 订阅变更写 Storage，重进小程序恢复；摊位歇业(`offline`) 时禁用加购。

### 4.4 结算对接

「去结算」→ 跳 `reserve` 页 → 组装 `items:[{productId, quantity}]` 调 `order.reserve`（已实现，含快照/库存原子扣减/优惠券核销）→ 成功后 `cart.clear()`。

## 五、商品预定码 · 定金支付 · 制作队列

### 5.1 现状（已实现）

`order` 云函数 `reserve` 已完成核心闭环：
- **取货码生成** `genPickupCode()` → `PICK-XXXX`（4 位，去除易混淆 `0O1I`），落 `orders.pickupCode`（`uk_pickup_code` 唯一）。
- **原子库存预扣** `deductStock`：`where({_id, stock:_.gte(qty), deletedAt:null}).update(inc)` 判 `stats.updated>0`，防超卖。
- **明细快照** 写 `order_items`（`productName/price` 快照防改名改价）+ `inventory_logs`（reason='reserve'）。
- 订单状态机：`pending → confirmed → completed`，另有 `cancelled`（`cancel` 回滚库存）。摊主 `confirm` 接单、`complete` 核销（支持按取货码）。

### 5.2 到店自提核销流程

```
顾客下单(reserve) → 生成取货码 PICK-XXXX
  → 摊主端 order-manage「待处理」收到新单
  → 摊主 confirm(备货中) → 推入制作队列
  → 顾客到摊报取货码 → 摊主 complete(按 pickupCode 核销) → 完成
```

制作队列即摊主端 `order-manage` 的 Tab 视图：`pending`（新单待接）/ `confirmed`（制作中）/ `completed`（已取）。建议增加**声音/震动新单提醒** + 待处理数角标。

### 5.3 定金支付（**已决策：暂缓，保持免定金**）

效果图「30 秒预订 · 线下提货扫码付」当前是**预约不付款**，且本期确定**沿用免定金到店自提**闭环——微信支付需企业主体商户号 + 入驻审核，属重资产，放到三期。以下为将来引入定金锁定履约（防放鸽子）时的设计存档：

| 项 | 设计 |
| ---- | ---- |
| 定金比例 | `orders` 增 `depositAmount`；摊主可配「无需定金 / 定金 N 元 / 全额预付」 |
| 支付通道 | `payment` 云函数封装微信支付统一下单 + 回调；`payments` 集合记 `transactionId/prepayId/status` |
| 尾款 | 到店扫码付尾款（`channel='offline_qr'`），或全额预付则免尾款 |
| 违约金 | `orders.penaltyAmount`（字段已预留）：顾客爽约扣定金，摊主未备货退定金 |
| 退款 | 拼团未成团、摊主取消 → `payment` 退定金 |

### 5.4 摊主收单通知（订阅消息，待建）

- 顾客 `reserve` 时前端 `Taro.requestSubscribeMessage` 申请「新订单/成团」模板授权。
- `order.reserve` 成功后云端 `subscribeMessage.send` 推给摊主：含商品、数量、取货码、预约时间、备注。
- 通知统一入 `notifications` 集合（type='order'），摊主端消息中心可回看。

### 5.5 待建清单

`payment` 云函数（微信支付下单/回调/退款）、订阅消息模板申请与下发、`orders.depositAmount` 字段、`order-manage` 新单实时提醒。

## 六、用户许愿池

### 6.1 现状（已实现）

`wish` 云函数已完整实现，页面 `wish-pool`：
- `create` 顾客许愿（内容过 `msgSecCheck`）
- `list`：`stallId=xxx` 看某摊许愿（带「我是否已点赞」）；`hot=true` 全站热度榜
- `reply` 摊主回愿（设状态 / 预定价 `expectPrice` / 到货时间 `expectArrive`，回复文本过检测）
- `like` 点赞/取消点赞（toggle，`wish_likes` 唯一约束一人一次）

### 6.2 数据模型

```
wishes:     { stallId, userId, content, status: pending|preparing|arrived|declined,
              vendorReply, vendorReplyAt, expectPrice, expectArrive, likes }
wish_likes: { wishId, userId }   // uk(wishId,userId)，点赞去重
```

### 6.3 竞品参考

类似**小红书评论区 + 闲鱼「我想要」求购**：评论式 UGC + 点赞排序。本项目做成**双向许愿池**——顾客许愿，摊主可回馈「能到货 + 预定价 + 到货时间」，直接把需求转成进货指导与预约钩子（差异化亮点）。

### 6.4 顾客侧

- 发表许愿（对本店的期望/想要的商品）。
- 看其他顾客许愿列表，支持**点赞**。
- **排序**：默认按 `likes` 倒序（热度），可切「最新」（`createdAt` 倒序）——对应 `list` 排序参数。
- 点赞 toggle 实时更新计数与自身点赞态。

### 6.5 摊主侧

- 在店铺后台看本摊许愿（可按热度看高频需求，指导进货）。
- 回愿：置状态（备货中/已到货/暂无法满足）+ 标注预定价与到货时间。
- **增强建议**：许愿状态转 `arrived` 时，给点赞过该愿的顾客推「到货提醒」订阅消息，并可一键转为可预约商品，闭环到模块四/五。

### 6.6 内容安全

所有文本（许愿内容、摊主回复）过 `msgSecCheck` v2；检测接口异常时放行并记录，不阻断主流程（与 `coupon`/`wish` 现有实现一致）。

## 七、落地路线图

### 7.1 已就绪（可直接联调）

店铺简介、优惠券（创建/领取/核销）、许愿池（许愿/回愿/点赞）、预定取货码（下单/接单/核销/库存原子扣减）。

### 7.2 需新建

| 优先级 | 事项 | 类型 |
| ---- | ---- | ---- |
| P0 ✅本期 | `cartStore` + `CartBar` 底部结算栏（模块四） | 前端 |
| P0 ✅本期 | `groupbuy` 云函数 + `groupbuyStore` + 摊主 `groupbuy-manage`（模块三） | 全栈 |
| P1 | 拼团到期定时触发器（云开发定时器扫 `expireAt<now` 置 expired） | 云函数 |
| P1 | 订阅消息：新订单/成团/到货提醒 | 云函数+前端 |
| P2 | 店铺主页聚合接口 `stall.detailBundle`（可选性能优化） | 云函数 |
| P2 | 收款自动发券（`order.complete` 挂 `auto_pay` 发券） | 云函数 |
| P2 | `rating` 真实聚合（订单完成好评） | 云函数 |
| P3 | `payment` 云函数（定金/尾款/退款）+ `orders.depositAmount`（需微信支付商户号，暂缓） | 全栈 |

### 7.3 分期建议

- **一期**：模块一/二/四/六 + 预定取货码闭环（无定金）→ 完整「逛店-加购-预约-到店自提-领券-许愿」体验。
- **二期**：模块三邻里拼团 + 订阅消息触达 + 收款自动发券（社交裂变与复购）。
- **三期**：模块五定金支付/退款 + 拼团退款 + 到货提醒（履约与资金能力）。
